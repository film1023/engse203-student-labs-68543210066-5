1. Component ใดเป็น state owner ของ tasks และ statusFilter เพราะเหตุใด?

2. ระบุตัวอย่าง Props ลงอย่างน้อย 2 จุด และ callback event ขึ้นอย่างน้อย 1 จุด

3. เมื่อนำ pattern ไปใช้ LAB 4 ต้องเปลี่ยน data contract, validation และ component responsibility อย่างไร?

   คำตอบ: ต้องขยายฟิลด์ข้อมูลเพิ่ม เช่น ลำดับความสำคัญ (Priority), วันที่สิ้นสุด (Due Date) และต้องทำระบบ Validation ตรวจสอบความถูกต้องเพื่อไม่ให้พิมพ์ค่าว่างส่งเข้ามา หรือป้องกันอักขระพิเศษที่เป็นอันตราย

### 📝 Check Understanding (05 — Props)

1. Props เป็น read-only หมายความว่าอย่างไร
คำตอบ: หมายความว่า Component ลูก (Child) มีสิทธิ์แค่รับค่าไปอ่านและแสดงผลบนหน้าจอเท่านั้น ไม่สามารถแก้ไขหรือปรับเปลี่ยนค่าใน Object ของ Props โดยตรงได้ หากต้องการเปลี่ยนค่า ต้องส่งสัญญาณผ่าน Callback เพื่อให้ Component แม่ (Parent) เป็นคนจัดการอัปเดตให้

2. เหตุใด Child จึงส่ง id กลับผ่าน callback
คำตอบ: เพราะตัวแปร State หลักถูกเก็บรวมกันเป็นกลุ่มข้อมูล (Array) อยู่ที่ Component แม่ ตัวแม่จึงจำเป็นต้องทราบ ID ของชิ้นงานเฉพาะเจาะจงที่ระบุได้แน่นอน เพื่อที่จะได้นำ ID นั้นไปค้นหาและสั่งลบหรือแก้ไขข้อมูลได้ถูกใบ ไม่สลับรายการกัน

3. onClick={onDeleteTask(task.id)} ผิดอย่างไร
คำตอบ: ผิดเพราะการใส่เครื่องหมายวงเล็บ `()` ต่อท้ายฟังก์ชันแบบนั้น จะทำให้ React สั่งรันฟังก์ชันลบทันทีตั้งแต่ตอนโหลดหน้าเว็บครั้งแรก (โดยที่ผู้ใช้ยังไม่ได้กดคลิกปุ่มเลย) รูปแบบที่ถูกต้องจึงต้องเขียนครอบด้วย Arrow function เป็น `onClick={() => onDeleteTask(task.id)}` เพื่อสั่งให้ระบบรอจนกว่าจะมีการกดคลิกจริงๆ ค่อยเริ่มทำงาน

### 📝 Check Understanding (07 — List & Key)

1. map() คืนค่าอะไร
คำตอบ: คืนค่าเป็น Array ใหม่ที่บรรจุ JSX Element (หรือ React Component) ที่ผ่านการแปลงโครงสร้างมาจากข้อมูลของแต่ละ Object ใน Array ต้นทางแล้ว เรียบร้อยเพื่อนำไปแสดงผลบนหน้าจอ

2. ทำไม stable key จึงสำคัญเมื่อมีการลบ
คำตอบ: เพราะ React ใช้ค่า key นี้เป็นเอกลักษณ์ (Identity) ในการเปรียบเทียบว่าคอมโพเนนต์ไหนเป็นรายการเดิม ชิ้นใหม่ หรือถูกลบออกไป หากไม่ใช้ key ที่คงที่ (เช่น ไปใช้ index หรือ Math.random) เวลาที่มีการลบหรือสลับลำดับการ์ด อาจทำให้ React สลับสถานะ (State) หรือโฟกัสไปอยู่ผิดรายการ และทำให้การแสดงผลบนหน้าจอเพี้ยนได้

3. Summary ควรใช้ tasks หรือ filteredTasks หากต้องแสดงภาพรวมทั้งหมด
คำตอบ: ควรใช้ 'tasks' ตัวหลักที่ยังไม่ผ่านการกรองครับ เพราะแผงภาพรวม (Summary) มีหน้าที่รายงานสถิติตัวเลขของงานทั้งหมดที่มีอยู่จริงในระบบแดชบอร์ด ไม่ใช่รายงานเฉพาะงานส่วนที่ถูกคัดกรองเลือกแสดงผลบนหน้าจอในขณะนั้น

### 🎟️ Exit Ticket (09 — Guided Build Summary)

ให้เติมคำหลักลงในช่องว่างตามประมวลความเข้าใจหลักการ React:

1. State หลักอยู่ที่: [ App ] (หรือ Parent Component ตัวบนสุดที่ครอบคลุมลูกทั้งหมด)
2. Child อ่านข้อมูลผ่าน: [ Props ] (ที่ไหลจากบนลงล่าง)
3. Child ขอให้ Parent เปลี่ยนข้อมูลผ่าน: [ Callback Function ] (หรือ Event Handling ที่ส่งย้อนกลับขึ้นบน)
4. List สร้างจาก array ด้วยคำสั่ง: [ .map() ] (พร้อมระบุ stable key)
5. Form field ถูกควบคุมด้วยกลไก: [ value ] + [ onChange ] (เรียกว่า Controlled Component)

### 📝 Check Understanding (10 — Transfer to LAB04)

1. ทำไม TaskForm จึง copy ไปใช้ตรงๆ ไม่ได้
คำตอบ: เพราะโครงสร้างข้อมูล (Data Contract) และกฎเกณฑ์ความปลอดภัย (Validation Rules) ของแบบฟอร์มแจ้งซ่อมเปลี่ยนไปโดยสิ้นเชิง จากเดิมที่มีเพียงชื่องานและหมวดหมู่ ต้องถูกออกแบบใหม่ให้รองรับถึง 5 ฟิลด์หลัก ได้แก่ ชื่อผู้แจ้ง (requesterName), ประเภทบริการ (requestType), สถานที่ (location), รายละเอียด (details), และระดับความสำคัญ (priority) อีกทั้งมีความยาวของตัวอักษรที่ดักจับเข้มงวดกว่าเดิม

2. RequestCard ควรเปลี่ยน requests state เองหรือไม่
คำตอบ: ไม่ควรอย่างยิ่งครับ เพราะขัดต่อหลักการ One-way Data Flow (ข้อมูลไหลลง เหตุการณ์ไหลกลับ) ตัวการ์ดมีหน้าที่เพียงรับข้อมูลผ่าน Props มาแสดงผลเท่านั้น หากต้องการลบหรือแก้ไขสถานะ ต้องใช้วิธีส่งรหัสไอดีผ่าน Callback function ขึ้นไปบอก Component แม่หลัก (App) ซึ่งเป็นเจ้าของ State ตัวจริงให้จัดการเปลี่ยนแปลงข้อมูลให้ครับ

3. หาก summary ไม่เปลี่ยนหลังเพิ่ม request ควรตรวจจุดใดก่อน
คำตอบ: ควรตรวจสอบที่ฟังก์ชันการบวกเพิ่มข้อมูลแบบ Immutable ใน Component แม่หลัก (App) ว่ามีการใช้ตัวแปรอัปเดต State ผิดพลาด หรือเผลอใช้คำสั่งแก้ไขอาเรย์ตรงๆ เช่น .push() หรือไม่ และต้องเช็กว่าแผง SummaryPanel คำนวณยอดสรุปจาก State หลักชุดล่าสุดตัวแปรถูกต้องหรือเปล่า

### 📝 Check Understanding (11 — Build & Submission)

1. ก่อนสั่ง Production Build เพราะเหตุใดต้องตรวจเช็กค่า base: './' ในไฟล์คอนฟิกวิเต้ (vite.config.js) zawsze?
คำตอบ: เพื่อกำหนดให้ตัว Vite ทำการคอมไพล์พาธของไฟล์โครงสร้าง (Assets เช่น CSS, JS) ออกมาเป็นในรูปแบบ Relative Path (พาทสัมพัทธ์) ซึ่งเป็นสิ่งจำเป็นอย่างยิ่งต่อการนำโปรเจกต์ของแต่ละสัปดาห์ไปเปิดรันเชื่อมโยงออนไลน์อยู่ภายใต้ระบบจัดเก็บส่วนกลาง (Pages Hub) หากไม่ใส่ตัวแปรนี้ ระบบคลาวด์จะหาไฟล์ตกแต่งไม่เจอและแสดงผลหน้าจอเป็นสีขาว (เกิด Asset 404 Error)

2. เหตุใดโครงสร้างโฟลเดอร์ปลายทางจึงแยกฝั่งอย่างชัดเจนระหว่าง source/ และ publish/ ในระบบ?
คำตอบ: เพื่อแยกกระบวนการอย่างเด็ดขาด โดยโฟลเดอร์ 'source/' มีไว้จัดเก็บโค้ดดิบและเครื่องมือช่วยพัฒนาสำหรับตัวนักศึกษาในการเขียนและรันทดสอบระบบ ส่วนโฟลเดอร์ 'publish/' และ 'docs/' จะจัดเก็บเฉพาะไฟล์ผลลัพธ์สุดท้ายที่ผ่านการบีบอัดและคอมไพล์เสร็จเรียบร้อยแล้ว (Production Build Output) เพื่อพร้อมสำหรับนำไปเปิดเป็นหน้าเว็บไซต์ออนไลน์บนคลาวด์โดยตรง ทำให้โครงสร้างคลังจัดเก็บไฟล์สะอาด ไม่ปะปนกับโค้ดขยะจำพวก node_modules

3. ข้อดีของการตรวจเช็กผลลัพธ์หน้าเว็บ Pages บนโหมดไม่ระบุตัวตน (Incognito Mode) คืออะไร?
คำตอบ: เพื่อป้องกันไม่ให้ข้อมูลแคชเดิม (Browser Cache) ที่เคยจำอยู่บนเครื่องคอมพิวเตอร์ของเราเข้ามาหลอกตา การเปิดดูผ่านโหมดไม่ระบุตัวตนจะช่วยจำลองพฤติกรรมจริงเหมือนกับตอนที่อาจารย์ผู้สอนเข้ามาเปิดคลิกตรวจงานจากภายนอกครั้งแรก ทำให้เรามั่นใจได้ 100% ว่าหน้าเว็บสามารถดาวน์โหลดซอร์สและแสดงผลความสวยงามได้อย่างครบถ้วนโดยไม่มีส่วนใดตกหล่น
